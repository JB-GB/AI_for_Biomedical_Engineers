## Actions
- **`Mejorar en este equipo`** (tab "Mejorar el modelo"):
  - Runs `python -m rausnet.improve run --progress` on the shared workspace, from this computer.
  - It is enabled only when PyTorch and a CUDA GPU are found. When disabled, the reason is shown in
    words (no GPU, training not installed, inference-only bundle, shared folder not on this computer).
  - The GPU check runs in a child process, so importing PyTorch never freezes the window.
  - Below the new-image threshold the app asks first, as for Colab. If another run holds the workspace
    lock (Colab, the lab server, another PC), the app says where and does not start.
- **Progress and cancel:**
  - `improve` reports stages (checking, staging, training with the number of rounds, publishing).
  - The app shows one sentence per stage ("Entrenando: ronda 1 de 4") and a percentage bar. Each stage
    is announced to screen readers once; epochs are not, to avoid noise.
  - `Cancelar mejora` asks for confirmation, then stops the run. The model in use never changes: the
    registry is published last.
- **Decision: child process (`QProcess`) instead of a `QThread`.**
  - A Python thread cannot be stopped safely in the middle of training; a process can be killed, and
    its GPU memory is freed when it ends.
  - After a cancel or a crash the app removes the workspace lock if that run held it. The run is
    identified by `RAUSNET_RUN_ID`, not by process id: on Windows a venv `python.exe` is a launcher, so
    its pid differs from the training process. The staging folder is always deleted.
  - Closing the window cancels a running improvement cleanly.
- **Version history:** a table of every registered version, newest first. Columns: version, date,
  status in words (`en uso`, `anterior`, `no aprobada`, plus "(este equipo)" for the served one),
  quality in words. History lines now include roll backs.
- **Roll back (lead option):**
  - `Ajustes → Opciones de responsable` shows `Volver a esta versión`. It only prevents accidental use;
    real access control is the permission on the shared folder.
  - Only archived versions with `model.onnx` can be chosen; rejected candidates cannot.
  - The app asks for confirmation and an optional reason (no patient data).
  - `POST /model/rollback` loads the old model **before** writing the registry, so a broken old version
    changes nothing. It then switches the registry under the workspace lock (never during an
    improvement), logs `rolled back` in `improve_log.jsonl` and serves the version at once.
  - CLI: `python -m rausnet.improve versions|rollback|gpu`.

## Results
- 11 new tests (`tests/test_local_improve.py`) plus progress stages in `test_improve.py`. 186 tests pass.
  - rollback: registry switch, log, refused for rejected, unknown or locked; API 404/409/422/503, model
    swapped, broken version leaves registry and served model unchanged;
  - lead-only button, rejected rows not selectable, cancel of the reason dialog changes nothing;
  - local run with a fake training process: monotonic progress up to 100 %, result sentence, staging
    deleted; cancel frees the lock and staging; a crash shows the error and frees the lock; refused while
    Colab holds the lock.
- **Real run on this laptop** (RTX 4070 Laptop GPU, small synthetic workspace, ResNet-18, 96 px):
  1. bootstrap v0001 through the app's runner: stages 2 → 5 → 10 → 38 → 66 → 95 → 100 %;
  2. 30 corrections added, `Mejorar en este equipo` from the window, v0002 promoted, new-model banner shown;
  3. roll back to v0001 as lead: served at once, history shows the roll back, no lock left.

## Correction during the work
- During a local run the panel still said "Ninguna mejora en curso": the status was read before the child
  took the lock. The panel now shows "Mejora en curso en este equipo" while its own run is active.

## Note for users
- After a roll back, the corrections used only by the newer version count as new again (they are not in
  the old version's dataset). The next improvement trains from the rolled-back version with them.
